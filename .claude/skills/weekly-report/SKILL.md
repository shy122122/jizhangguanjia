# 明账项目周报生成

把一周的 git 提交整理成一份可读的周报。**机器负责算数和取数，你负责归纳和写作** ——
日期区间、提交明细、行数统计一律来自脚本输出，不要自己心算或估算。

## 输出

- **位置**：`D:\workspace\my projects\周报汇总\`
- **文件名**：`<周一>_<周日>-周报.md`，例如 `2026-09-21_2026-09-27-周报.md`
- **同名已存在时直接覆盖** —— 同一周重复生成不该堆出一堆近似文件

## 步骤

### 1. 确定统计周期

```bash
node ".claude/skills/weekly-report/scripts/week-range.js"
```

输出 JSON：

```json
{ "monday": "2026-09-21", "sunday": "2026-09-27",
  "since": "2026-09-21 00:00:00", "until": "2026-09-27 23:59:59",
  "label": "2026-09-21_2026-09-27", "isoWeek": "2026-W39",
  "weekNo": 39, "base": "2026-09-26", "baseWeekday": "周六" }
```

要出**某一周**的周报（补写、或用户指定日期），把那个日期传给脚本：

```bash
node ".claude/skills/weekly-report/scripts/week-range.js" 2026-09-23
```

> **不要自己推算周一/周日。** 跨月、跨年那几周极易算错，而日期区间一旦错了，
> 整份报告就没有对照价值。这类确定性计算交给脚本。

### 2. 采集提交

把上一步的 `since` / `until` 原样传进去（注意带引号，含空格）：

```bash
node ".claude/skills/weekly-report/scripts/collect-commits.js" \
  --since "2026-09-21 00:00:00" --until "2026-09-27 23:59:59"
```

输出 JSON，关键字段：

| 字段 | 含义 |
|---|---|
| `source` | `local` / `remote` / `none` —— 提交是从哪读到的 |
| `note` | 采集过程中的说明（如"本地无提交，已改读远端"），非 null 时**要在报告开头说明** |
| `commits[]` | 每个提交：`hash` `author` `date` `subject` `body` `type` `scope` `files` `insertions` `deletions` `primaryModule` `primaryLabel` `modules` `topFiles` |
| `summary` | 提交数、涉及文件数、新增/删除行、作者 |
| `byModule` / `byDay` / `byType` | 按模块 / 按天 / 按提交类型的聚合 |
| `workingTree` | **未提交的改动**，按模块分组（含 `files` `insertions` `deletions` `samplePaths`） |
| `lastCommit` | 全仓库最近一次提交，空周报时作参照 |

**数据源策略**（脚本已内置，无需你干预）：先读本地 `git log`；本地这一周没有提交时，
自动 `git fetch` 再读远端 `origin/main`。结果体现在 `source` 字段里。

### 3. 处理「本周没有提交」

`commits` 为空数组时，按下面顺序处理，**不要直接交一份空报告**：

1. **看 `workingTree`。** 本地这周没提交，不代表没干活 —— 工作区里往往正躺着
   这一周真正在写的东西。有未提交改动时，报告里**单开一节「进行中的工作（未提交）」**，
   并在开头说明本周提交为空、内容来自工作区。
2. **连未提交改动也没有**，照实写「本周无提交」，并用 `lastCommit` 列出最近一次提交
   作为时间参照。
3. **任何时候都不要编造内容。** 宁可交一份诚实的短报告。

### 4. 归类

按**改动文件路径**（脚本已算好的 `primaryModule`）归入下表 6 个方向。
路径比 commit message 可靠：一个提交改了什么文件是事实，写的是什么标题是修饰。

| `primaryModule` | 报告里的标题 | 路径前缀 |
|---|---|---|
| `PRD` | 需求与设计 · PRD | `PRD/` |
| `UI` | 需求与设计 · UI 原型 | `UI原型（美术设计）/` |
| `frontend` | 前端开发 | `前端代码（前端工程师）/` |
| `admin` | 后台管理系统（运营端） | `后台管理系统（运营专员）/` |
| `backend` | 后端服务 | `后端代码(JAVA工程师)/` |
| `database` | 数据库 | `数据库脚本/` |
| `docs` | 其他 | 其余 |

- 一个提交跨多个模块时归入改动文件最多的那个（脚本已判定），
  在该条后用 `（另涉及 <模块>）` 点一句即可。
- **某个模块本周没内容就整节省略**，不要写「本周无」凑篇幅。

### 5. 写作要求

- 用**产品 / 工程语言**说清「做了什么、为什么做」，**不要罗列文件路径**。
- **把同一主题的多个提交合并成一条。** 周报读者关心"这周推进了什么"，
  不是提交流水账；同一个功能拆成 8 个提交也只写一条。
- commit 的 `type`（feat / fix / docs / chore）只用来判断语气和分量，不要照抄进正文。
- 数字、日期、金额**逐字取自脚本输出**，不要四舍五入或估算。
- 「下周计划」一节**只在提交或未提交改动里能看出明确未完成项时才写**；没有依据就整节省略。

### 6. 落盘并回报

写到目标路径后，向用户回报：

1. 报告的**完整路径**
2. 本周要点 1~2 句（主线是什么、推进到哪一步）

## 报告模板

```markdown
# 明账项目周报 · {isoWeek}

> 统计区间：{monday} ~ {sunday}（周一 ~ 周日）
> 数据来源：{本地 git / 远端 origin/main} · 共 {commitCount} 次提交
> 生成时间：{今天}

## 一、本周概要

{2~4 句话讲清本周主线：在推进什么、到什么程度。不要复述下面的条目。}

## 二、需求与设计（PRD / UI 原型）

- **{主题}** — {做了什么、为什么}

## 三、前端开发

- **{主题}** — {做了什么、为什么}

## 四、后台管理系统（运营端）

- ...

## 五、后端服务

- ...

## 六、数据库

- ...

## 七、进行中的工作（未提交）

> 本节仅在工作区有未提交改动时出现；本周提交为空时，本报告以本节为主。

- **{模块}** — {在做什么}（{n} 个文件）

## 八、汇总统计

| 指标 | 数值 |
|---|---|
| 提交次数 | {commitCount} |
| 涉及文件 | {files} |
| 新增 / 删除行 | +{insertions} / -{deletions} |
| 提交日期分布 | {byDay，如 09-23(1)、09-24(2)} |
```

## 注意事项

- **本仓库 git 历史极稀疏**：目前只有一个 `chore: 初始化明账项目存档` 提交，
  其余工作全在工作区里未提交。**不要因为提交少就怀疑脚本出错** —— 这是仓库的真实状态，
  也正因如此，「进行中的工作（未提交）」这一节格外重要。
- 以下路径段的文件**不计入统计**（脚本按路径段过滤，出现在任意层级都排除）：
  `周报汇总`（输出目录，算了会自我循环）、`.claude`（工具配置，不是项目成果）、
  `node_modules` / `.npm-cache` / `.git`（依赖与缓存，动辄数百条，会把真实改动淹掉）。
  本仓库的 npm 缓存就埋在 `后台管理系统（运营专员）/backend/.npm-cache/` 下，共 367 个文件 ——
  不过滤掉的话，周报会把一半篇幅花在这堆缓存上。
- 不要在报告里出现 token、密钥、密码；涉及用户数据时用脱敏形式（手机号 `138****1234`）。
- 脚本输出的路径若出现 `�` 之类的乱码字符，那是管道转码的显示问题、不是仓库里的坏文件，
  直接忽略该条即可。

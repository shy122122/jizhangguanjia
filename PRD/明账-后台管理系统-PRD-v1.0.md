## ⛔ 硬约束：现有数据库结构一个字都不改

本项目的数据库结构已经冻结。以下内容**在任何情况下都不得改动**：

| 冻结对象 | 出处 | 数量 |
| --- | --- | --- |
| 业务表 | `01_schema.sql` | 12 张 |
| 视图 | `03_views.sql` | 6 个 |
| CHECK 约束 | `01_schema.sql` | 8 条 |
| 索引、外键、列定义 | `01_schema.sql` | 全部 |

**禁止的操作**：`ALTER TABLE`（加列 / 改列类型 / 改默认值 / 改约束 / 加索引）、`DROP TABLE`、`DROP VIEW`、`RENAME`。后台对现有表的动作只有 `SELECT` / `INSERT` / `UPDATE` / `DELETE` —— 即**只改数据，不改结构**。

**唯一允许的结构变更**：`CREATE TABLE` 新建**属于后台自己的独立新表**（清单见 5.2）。

### 这条约束推导出的三条硬规则

| # | 规则 | 为什么 |
| --- | --- | --- |
| R1 | 后台的新表**不得对 C 端表建外键** | 外键的 `RESTRICT` 会挡住 C 端注销时的级联删除，`SET NULL` 又会丢追溯信息。后台表与 C 端表只在**业务逻辑层**关联，不在数据库层绑定 |
| R2 | 后台**不得依赖 C 端表的新增列** | 既然不能 `ALTER`，就不存在新列。后台的身份、权限、配置只能落在自己的新表里 |
| R3 | 后台表的生命周期与 C 端**解耦** | 用户注销时 C 端会级联物理删除数据，但**不会**（也不应该）删掉后台的审计记录。这正是 `admin_audit_log.target_label` 要冗余存 `uid` / 手机号的原因（见 5.2） |

> **易混淆点：改数据 ≠ 改结构。** 后台「停用用户」写的是 `UPDATE user SET status = 2` —— 这是改**数据**，完全符合约束，且这正是用户管理模块的核心能力。被禁止的只是改**结构**（列、约束、索引、表本身）。

## 1. 产品概述

### 1.1 一句话定位

面向运营专员的内部管理后台：**处置用户账号、查阅用户数据、维护全局运营配置、观测产品指标**。

它不产生任何面向用户的界面，也不参与记账主流程。

### 1.2 为什么需要它

C 端已经能把账记起来，但产品缺少「有人管」的能力。三个具体缺口：

| # | 缺口 | 现状证据 |
| --- | --- | --- |
| 1 | **账号无法处置** | `user.status` 有 1正常/2停用/3注销 三态，`login_fail_count`/`locked_until` 有锁定机制，但全项目没有任何界面能改它们。用户被锁 15 分钟只能干等；违规账号无法停用 |
| 2 | **数据无法自证** | 用户报「我的账对不上」时，客服只能让他自己截图。没有只读的排查视图，也没有跨用户的检索能力 |
| 3 | **配置改不动** | 关键词自动分类规则存在 `category_rule` 表里（运营改不了，因为没界面）；分类与账户模板更是**硬编码在代码常量里**（`auth.service.js` 的 `DEFAULT_CATEGORIES` / `DEFAULT_ACCOUNTS`），加一个默认分类必须改代码 + 重新部署 |

### 1.3 与 C 端的根本差异：一次架构反转

**这是本后台最重要的设计约束，后面所有安全设计都从它推导出来。**

C 端的每一条 SQL 都必须带 `ledger_id = ?` 做租户隔离 —— 这是 C 端 PRD 第 11 章列为「高危风险」的红线，C 端后端也确实是这么实现的（`middleware/auth.js` 顶部的注释把这条写成了安全底线）。

而后台恰好相反：**它要跨账本、跨用户地看数据。**

所以后台不是「C 端加几个页面」，而是**一套以更高权限运行的旁路系统**。三条派生约束：

1. **独立鉴权** —— C 端用户 token 不能换到后台权限。
2. **独立数据库账号** —— 后台账号可跨 ledger 读，但写权限被收窄到极少数列（见 3.2）。
3. **全量操作审计** —— 权限越大，留痕越严。

### 1.4 首期范围

**V1.0 要做（In Scope）**

- 后台独立登录
- 用户管理（列表 / 搜索 / 详情）
- 账户处置（停用、恢复、注销标记、解锁、强制下线、重置密码）
- 用户数据只读查看（账本 / 账户 / 分类 / 预算 / 流水 / 导入批次）
- 运营配置（关键词规则；分类与账户模板需先落表）
- 数据看板
- 操作审计日志

**V1.0 不做（Out of Scope）**

| 不做的事 | 原因 |
| --- | --- |
| 修改 / 删除用户的任何流水、预算、账户、分类 | 记账数据是用户的财务事实，运营改一笔就是篡改。见 3.5 红线 |
| 「以用户身份登录 / 模拟登录」 | 一次误操作就是顶替他人身份，风险与收益完全不成比例 |
| 物理删除用户 | C 端已有 `deleteAccount`（物理删 user + ledger + 级联），但那要求**用户本人输密码 + 手打 DELETE 确认**。运营不该有这个能力，见 4.2.3 |
| 导入监控 | 本期未选（依赖前端解析埋点，见 7 待定问题） |
| 多角色 RBAC | 本期单一角色，见 2.1 |
| 财务对账 / 结算类功能 | 本产品是个人记账，不涉及资金流 |

### 2.1 首期：单一角色「运营专员」

所有后台账号权限相同。理由：V1.0 运营团队规模小，RBAC 的表结构和页面控制成本远大于收益；后续加角色不算返工（见 8.1）。

后台账号由**超管手工建**（直接写库或一个隐藏的初始化脚本），不开放自助注册 —— 内部系统的账号创建本身就是敏感操作。

## 3. 安全与架构约束

> 本章是后台的**技术红线**，不是建议。写在这里是因为这几条一旦让步，后台就从「运维工具」变成「数据泄露源」。

### 3.1 独立鉴权，与 C 端 token 完全隔离

- 后台账号存**独立表** `admin_user`，与 C 端 `user` 表物理隔离，不复用同一张表加 `is_admin` 字段。
  - 理由：C 端 `user` 表是用户注册流程直接写入的，任何字段级的复用都可能被注册逻辑污染。
- 后台 token 的载荷带 `scope: 'admin'` 标记；后台的鉴权中间件**独立实现**，不复用 C 端的 `requireAuth`。
  - 理由：`requireAuth` 会去查 `ledger` 表并要求账号必须有账本（`middleware/auth.js:46`）。后台账号没有账本，复用必然要打补丁，而补丁就是漏洞的入口。
- **C 端 token 调后台接口必须被拒，后台 token 调 C 端接口也必须被拒** —— 双向都要测，只测一个方向是常见的疏漏。
- 后台建议**不部署在公网同一域名下**；至少要做到路径隔离 + 独立鉴权，有条件的加 IP 白名单。

### 3.2 独立数据库账号，用**权限**兜住产品约束

| 账号 | 读 | 写 |
| --- | --- | --- |
| `mz_app`（C 端，已存在） | 业务表 + 6 个视图 | 业务表（受 service 层逻辑约束） |
| `mz_admin`（后台，新增） | **全库可读**（跨 ledger） | **仅限下列列** |

`mz_admin` 的写权限**只开放这些列**：

- `user`：`status`、`token_version`、`login_fail_count`、`locked_until`
- `category_rule`：整表（仅 `ledger_id IS NULL` 的系统规则行，应用层保证）
- `category_template` / `account_template`：整表（新增）
- `admin_audit_log`：只允许 INSERT，不允许 UPDATE / DELETE

**明确不给 `mz_admin` 的写权限**：`transaction`、`budget`、`budget_category`、`account`、`category`、`ledger`、`import_batch`。

> **为什么用数据库权限而不是靠代码自觉**：产品规则「运营不能改用户流水」写在代码里是一行 `if`，下次有人加功能时很容易绕过；写成数据库的 `GRANT` 则是物理上做不到。「运营不能改流水」这条约束值得用后者的强度来保护。

**`mz_admin` 不给 DDL 权限。** `CREATE TABLE` 是「结构冻结」约束里唯一被允许的结构变更，但它**不应该**是运行时账号的能力 —— 一个代码缺陷若能让应用执行 `ALTER` / `DROP`，就恰好击穿了被禁止的那两条。正确做法是：新表的建立由**部署时的迁移脚本**用一个独立的、只在迁移窗口存在的高权限账号执行；应用运行时账号 `mz_admin` 只持有上表列出的 DML 权限。

**`mz_admin` 必须显式不授 `ALTER` / `DROP`**，让它对现有 12 表连「试图改结构」都做不到 —— 这样文首「硬约束」就不是一条纸面纪律，而是权限系统里的既成事实。

> 补充（MySQL 权限模型）：`CREATE`、`ALTER`、`DROP` 是**三个彼此独立的权限位**，`GRANT CREATE ON mingzhang.* TO mz_admin` 并不会顺带给出 `ALTER`。所以「只授权建新表」在技术上可行。但本项目仍建议**运行时账号一个 DDL 权限都不给**：`CREATE` 能建的不只是 `category_template`，而是**任意**表名 —— 一旦建错或建重，清理它又需要 `DROP`，等于把问题推给下次。建表这件事一次做好、走迁移，比留一个宽泛的应急口子更稳妥。

### 3.3 强制审计

每一次后台写操作，必须落一条 `admin_audit_log`。**不允许有例外**，包括看似无害的操作。

审计行必须能在**目标对象已被删除之后**仍然可读 —— 所以要冗余存一份操作时的对象标识（`target_label`，如 `9402-8841-CLARITY / 138****1234`），不能只存 `target_id`。

### 3.4 隐私边界与脱敏

已决策：**运营专员可以查看用户明细流水。**

这项决策的风险是运营会接触用户隐私，因此必须配套以下要求：

| 要求 | 说明 |
| --- | --- |
| 列表默认脱敏 | 手机号 `138****1234`、邮箱 `d***@mingzhang.app` |
| 搜索走精确匹配 | 脱敏后无法模糊搜，所以搜索框输入**完整**手机号/邮箱，后端精确匹配，命中后仍显示脱敏结果 |
| 查看明细留痕 | 每次打开某用户的流水明细，记一条 `user.data.view` 审计 |
| 导出需二次确认 | 导出用户数据必须填原因，且审计留痕 |

### 3.5 红线（写死，不做任何「灵活处理」）

1. **不修改用户的任何记账数据** —— 流水、预算、账户、分类一律只读。
2. **不做模拟登录** —— 不提供「以该用户身份查看」的能力。
3. **不物理删除用户** —— 只做状态标记。物理删除能力只属于用户本人（C 端 `deleteAccount` 要求本人密码 + 手打 `DELETE`）。
4. **不查看密码哈希与 token** —— 详情页不展示，接口不返回。
5. **不做「批量处置」** —— 首期只允许逐个操作。批量停用这类功能，误操作代价是不可逆的。
6. **不改数据库结构** —— 不对现有 12 表 / 6 视图 / 8 约束做任何 `ALTER` / `DROP` / `RENAME`，也不给它们加索引或外键；只能 `CREATE TABLE` 建后台自己的独立新表。详见文首「硬约束」。

## 4. 功能详细规格

### 4.1 后台登录

| 项 | 规格 |
| --- | --- |
| 方式 | 用户名 + 密码（不使用手机号/邮箱，避免与 C 端账号体系混淆） |
| 密码存储 | bcrypt（cost 10），与 C 端同规格 |
| 登录失败 | 连续 5 次锁定 15 分钟（**与 C 端一致的策略**，字段结构也照搬） |
| 会话 | 建议 8 小时过期（内部系统，不应像 C 端那样 30 天） |
| 记录 | 每次成功登录记 `last_login_at` + `last_login_ip` |
| 强制下线 | 递增 `admin_user.token_version`，旧 token 立即失效 |

登录失败计数、锁定、token_version 这三样 C 端已经跑通（`auth.service.js`），后台照搬同一套结构即可 —— 但**代码要独立**，不要为了省事去 import C 端的 auth service。

### 4.2 用户管理（核心模块）

#### 4.2.1 用户列表

**字段**

| 列 | 说明 |
| --- | --- |
| `uid` | 对外账号标识，形如 `9402-8841-CLARITY` |
| 昵称 | `display_name` |
| 手机号 | 脱敏 |
| 邮箱 | 脱敏 |
| 状态 | 正常 / 已停用 / 已注销 |
| 注册时间 | `created_at` |
| 最后登录 | `last_login_at`，从未登录显示「—」 |
| 异常标记 | 锁定中（`locked_until > NOW()`）或 失败 ≥ 3 次时高亮 |

**搜索**：uid / 手机号 / 邮箱 / 昵称，四选一。手机号与邮箱走**完整值精确匹配**（理由见 3.4）。

**筛选**

- 状态（正常 / 停用 / 注销）
- 注册时间区间
- 最后登录时间区间（含「从未登录」）
- 是否设置过预算
- 登录异常（锁定中 / 多次失败）

**排序**：注册时间、最后登录时间（升/降序）

**分页**：每页 20 / 50 / 100，默认 20。总数一并返回。

#### 4.2.2 用户详情

详情页分六个区：

| 区 | 内容 |
| --- | --- |
| ① 账号资料 | uid、昵称、头像、手机号（脱敏）、邮箱（脱敏）、注册时间、最后登录、状态 |
| ② 数据概览 | 账本数、账户数、分类数、流水笔数、最早/最晚流水时间、预算设置情况（哪些月份设过） |
| ③ 安全状态 | 登录失败次数、锁定截止时间、`token_version` 当前值、最近登录 IP |
| ④ 处置操作区 | 见 4.2.3，按钮需二次确认 + 原因必填 |
| ⑤ 数据浏览区 | 五个 Tab：账户 / 分类 / 预算 / 流水 / 导入批次，**全部只读** |
| ⑥ 该用户的操作历史 | 按 `target_id` 反查 `admin_audit_log`，让运营看到「这个账号之前被谁处理过」 |

第 ⑥ 区是刻意设计的：它让处置动作**可追溯、可交接**，避免两个运营对同一账号做出矛盾操作。

#### 4.2.3 账号处置（本模块的核心价值）

> 下表每个动作都对照过 C 端现有机制。**处置动作应复用 C 端 service 层的逻辑，但不应复用 C 端的鉴权入口** —— 因为 C 端这些函数都绑定「操作者 = 用户本人」。

| 动作 | 改什么 | 用户侧立刻的表现 | 可逆 |
| --- | --- | --- | --- |
| **解锁登录** | `login_fail_count = 0`，`locked_until = NULL` | 立刻可以正常登录 | ✅ |
| **强制下线** | `token_version + 1` | 当前所有设备的 token 立即失效，下次请求要求重新登录；账号本身仍可正常登录 | ✅ |
| **停用** | `status = 2`，`token_version + 1` | 登录被拒（`USER_DISABLED`）；**已登录的会话在下一次请求时也会被拒** —— 因为中间件每次都查库校验状态 | ✅ |
| **恢复** | `status = 1` | 可以正常登录 | — |
| **标记注销** | `status = 3` | 登录被拒（`USER_CANCELLED`） | ⚠️ 见下 |
| **重置密码** | `password_hash = 新值`，`token_version + 1` | 旧密码失效、所有旧会话失效；**新密码怎么交给用户需决策**（见 7 待定问题） | ✅ |
| **物理删除** | ❌ **后台不提供** | — | — |

**三个需要点名的实现细节：**

1. **停用后旧 token 会立即失效，靠的是中间件每次都查库。**
   C 端 `middleware/auth.js` 没有把授权信息塞进 token，而是每个请求现查 `user.status` —— 注释里写明理由就是「不能让封号推迟一个月生效」。这个设计让后台的停用动作天然是即时的，**不需要额外做什么**。

2. **「标记注销」与 C 端的 `deleteAccount` 是两件事，不要混。**
   C 端 `deleteAccount`（`auth.service.js:467`）会**物理删除** `event_log` → `ledger` → `user`（外键级联带走全部业务数据）。它要求用户本人输密码 + 手打 `DELETE` 确认。后台的「标记注销」只写 `status = 3`，**数据全部保留**。
   - 理由：物理删除不可逆，且会让审计日志失去目标对象。运营误点一次的代价是用户全部财务记录消失。
   - 如果确实有合规要求的「彻底删除」，应当走**独立的申请审批流程**，由超管在数据库层执行，而不是后台的一个按钮。

3. **重置密码必须同时递增 `token_version`。**
   否则旧密码虽然改了，但用户在其他设备上已经登录的会话仍然有效 —— 这正好是与「密码泄露」场景最相关的时候。

#### 4.2.4 用户数据只读浏览

五个 Tab 的数据来源全部是 C 端已有的表与视图，后台只做展示，不重新定义口径：

| Tab | 数据来源 | 说明 |
| --- | --- | --- |
| 账户 | `v_account_balance` | **信用卡要读 `credit_used` / `credit_available`，不要读 `balance`** —— 信用卡的 `balance` 是净资产口径的负值，取错列整个页面就错了 |
| 分类 | `category` | 含系统预设与用户自建，标出 `is_system` |
| 预算 | `budget` + `v_budget_category_progress` | 按月份列出 |
| 流水 | `transaction` | 需**显式区分**已软删除的流水（`is_deleted = 1`），默认不显示，可切换查看 |
| 导入批次 | `import_batch` | 含撤销状态与撤销时间 |

**口径一致性要求**：后台展示的金额、百分比必须与 C 端完全一致。所有金额一律走十进制定点（分）运算，不引入浮点；6 个视图已经建立的统计口径（如「转账不计入收支」）后台不得自行重算。

#### 4.2.5 数据导出

- 导出对象：单个用户的全部数据（对应 C 端 PRD 第 11 章「提供数据导出」的合规诉求）
- 格式：JSON（结构化）+ CSV（流水）
- 前置：填导出原因，记审计
- 限制：**不提供全量用户批量导出**

### 4.3 运营配置

#### 4.3.1 关键词自动分类规则（**表已就绪，成本最低、价值最高**）

`category_rule` 表中 `ledger_id IS NULL` 的行就是全局系统规则，所有账本共用。当前种子数据有 **64 条**规则，覆盖 9 个支出分类。

对应 C 端 PRD 第 11 章的对策：「解析逻辑做成可配置规则表」—— 表已经在了，缺的就是界面。

| 功能 | 说明 |
| --- | --- |
| 列表 | 按分类分组展示，显示关键词、`match_type`、`priority`、`is_system` |
| 新增 | 关键词 + 目标分类 + 匹配方式 + 优先级 |
| 编辑 | 改优先级、改目标分类、启用/停用 |
| 删除 | 物理删除（此表无软删字段） |
| **优先级预览** | 输入一个商户名（如「美团买药」），实时显示会命中哪条规则 |

**优先级规则必须解释清楚**，否则运营会误用：种子里刻意设了两档 —— 具体品牌 20/30 分、行业泛词 10 分，例如「美团买药」（30）必须压过「美团」（20），否则买药会被归到餐饮。界面上要能一眼看出这种竞争关系。

> ⚠️ **不要做「删除内置规则」的批量按钮**。种子脚本的清理段落里专门写了 `DELETE FROM category_rule WHERE is_system = 1` 需要产品决策 —— 删光内置规则会让新用户的自动分类完全失效。

#### 4.3.2 分类 / 账户模板（**需先落表**）

**现状**：新用户注册时复制的默认分类（16 个）和默认账户（5 个），**硬编码在 `auth.service.js` 的常量数组里**。源码注释写得很明确：

> 「默认分类与账户应当在【用户注册时】按模板复制」。所以模板的权威定义在这里，`02_seed.sql` 只是把同一份数据灌给演示账本。

**问题**：运营想加一个默认分类（比如「宠物」），必须改代码 + 走发布流程。

**方案**：新增两张模板表，`auth.service.js` 的注册逻辑改为从表读取（常量保留为兜底）。

```sql
category_template  (id, name, type, icon, color, sort_order, is_enabled, ...)
account_template   (id, name, type, icon, color, initial_balance,
                    credit_limit, bill_due, card_tail, is_default, sort_order, is_enabled, ...)
```

**必须写清楚的产品语义**：

- 模板变更**只影响变更之后新注册的用户**，不追溯已注册用户。界面上要明确提示这一点，否则运营会以为改了模板所有用户都变。
- 模板不能删到「一个分类都不剩」—— 至少要校验：支出分类 ≥ 1、收入分类 ≥ 1。
- 账户模板的 `credit_limit` 等字段要遵守与 `account` 表相同的约束（非信用卡账户的 `credit_limit` / `bill_due` 必须为空）。

**优先级**：账户模板可放二期。分类模板是运营更高频的需求。

### 4.4 数据看板

指标口径直接采用 C 端 PRD 第 9.3 节已定义的清单，不另起一套。

> ⚠️ **这张表的「现状」列是本模块最重要的信息**：10 个指标里有 3 个当前**没有数据来源**，必须先补埋点。

| 指标 | 数据来源 | 现状 |
| --- | --- | --- |
| 注册用户数 | `user` | ✅ 现成 |
| 有效账本数 | `ledger WHERE is_archived = 0` | ✅ 现成 |
| 流水总量 | `transaction WHERE is_deleted = 0` | ✅ 现成 |
| 人均日记账笔数 | `transaction` / `user` | ✅ 现成 |
| 周均记账天数（北极星） | `transaction.happened_at` 按用户去重计天数 | ✅ 可算 |
| 预算设置率 | 有 `budget` 记录的用户 / 总用户 | ✅ 现成 |
| 导入成功率 | `import_batch`：completed / 全部 | ✅ 现成 |
| **DAU / WAU** | 需要「每日活跃」记录 | ❌ **无来源** |
| **7 日 / 30 日留存** | 需要「某日注册的用户在 T+N 是否活跃」 | ❌ **无来源** |
| **记账耗时中位数** | C 端 PRD 9.2 的 `txn_created.duration_ms` | ❌ **无来源** |

**为什么没有来源**：`event_log` 表在 schema 里是【可选】的，而且经核查，**全后端只有一处引用它**（注销账号时删除该用户的事件），**没有任何地方写入**。也就是说埋点根本没落地。

**启用埋点需要先做的决策**（见 7 待定问题）：

1. `user.last_login_at` 只保留**最后一次**登录时间，所以它**算不出历史 DAU** —— 不能用它凑数。
2. 建议不要用 `event_log` 算 DAU/留存，而是新增一张**日活去重表** `user_daily_active(user_id, active_date)`，唯一键 `(user_id, active_date)`，由后端在鉴权中间件里「每天每人最多写一条」。理由：`event_log` 里的 `page_view` 是高频事件，用来算留存要扫大量行，且去重代价高；而日活表天然是聚合后的形态，留存查询只是一个自连接。
3. 最小埋点集（够算本期指标）：`txn_created`（含 `duration_ms`）、`signup_complete`、`budget_set`，加上上面的日活表。

### 4.5 操作审计日志

| 功能 | 说明 |
| --- | --- |
| 列表 | 按时间倒序，显示：操作人、动作、目标对象、原因、时间、IP |
| 筛选 | 操作人 / 动作类型 / 目标对象 / 时间区间 |

## 5. 数据模型

### 5.1 原则：只新增表，不改现有结构

`01_schema.sql` 的 12 表 / 6 视图 / 8 个 CHECK 约束是已经用 `_verify.sh` 全绿验证过的资产，**冻结**。后台的一切新增只走 `CREATE TABLE` 建**独立的新表**；对现有表只做 DML（读 / 写数据），不做任何 DDL。

| 动作 | 是否允许 |
| --- | --- |
| `CREATE TABLE`（后台自己的新表） | ✅ |
| `SELECT` / `INSERT` / `UPDATE` / `DELETE`（现有表） | ✅ |
| `ALTER TABLE` / `DROP` / `RENAME`（现有表或视图） | ❌ |
| 对现有表加索引、加外键、加触发器 | ❌ |

新表必须遵守文首「硬约束」里的 R1–R3：**不建外键指向 C 端表、不依赖 C 端新列、生命周期与 C 端解耦**。下表的 5 张新表全部按此设计。

### 5.2 需要新建的表

| 表 | 用途 | 必要性 |
| --- | --- | --- |
| `admin_user` | 后台账号 | **必须**，无它无法鉴权 |
| `admin_audit_log` | 操作审计 | **必须**，无它无法追责 |
| `user_daily_active` | 日活去重（看板前置） | 看板模块必需 |
| `category_template` | 分类模板落表 | 运营配置模块必需 |
| `account_template` | 账户模板落表 | 可二期 |

**`admin_user` 字段设计**（刻照 `user` 表的安全列，保持策略一致）：

```sql
id, username, password_hash, display_name,
status,               -- 1启用 2停用
token_version,        -- 强制下线用
login_fail_count, locked_until, last_login_at, last_login_ip,
created_at, updated_at
```

**`admin_audit_log` 字段设计**：

```sql
id, admin_id,
action,          -- user.disable / user.enable / user.unlock / user.logout_all
                 -- / user.reset_password / user.cancel / user.data.view / rule.create ...
target_type,     -- user / category_rule / category_template
target_id,
target_label,    -- 冗余：操作时的 uid/手机号，防目标被删后无法追溯
before_json, after_json,
reason,          -- 处置原因，必填
ip,
created_at
```

> `target_label` 的冗余不是可选项。审计日志的价值就在于事后追溯，如果它指向的对象已经不存在、或者被改名，日志就废了。

**关于 R1 的落地说明**：上表中 `admin_audit_log.admin_id`、`target_id`、`user_daily_active.user_id` 虽然语义上是「指向某张表的某一行」，但**一律不建外键**。写库时靠 service 层保证引用有效；`admin_user.id` 与 C 端 `user.id` 是**两套完全独立的 ID 空间**，数值相同不代表任何关联。

同理，`user_daily_active` 只存 `user_id` 与 `stat_date` 两个裸值 + 计数，不存任何 C 端表的外键引用 —— 它要回答的问题只是「某天有多少个不重复用户活跃」，用户注销后这行统计**仍然保留**。

### 5.3 需要新增的查询

后台的聚合维度是**「用户」**，而现有 6 个视图全是 **`ledger_id` 级**的。所以后台需要新写一批跨账本的聚合查询（不必是视图，service 层的 SQL 即可）：

- 用户维度的流水笔数与时间跨度
- 用户是否设过预算
- 看板的日活 / 留存统计

**这些查询只存在于后台代码里，不要污染 C 端的 service。**

## 6. 关键设计决策记录

| # | 决策 | 理由 |
| --- | --- | --- |
| 1 | 后台账号用独立表，不用 `user.is_admin` | C 端 `user` 表的写入路径是公开注册流程，字段级复用会被注册逻辑污染 |
| 2 | 后台鉴权中间件独立实现，不复用 `requireAuth` | `requireAuth` 强依赖「账号必须有账本」，后台账号没有账本，强行复用要打补丁，补丁即漏洞 |
| 3 | 运营**不能**修改用户记账数据 | 财务数据的中立性是产品的底层立场，改一笔就是篡改 |
| 4 | 后台只做「标记注销」，不做物理删除 | 物理删除不可逆，且会让审计失去目标。彻底删除应走独立审批 |
| 5 | 用数据库权限而不仅是代码约束 | 代码里的一行 `if` 容易被后人绕过，`GRANT` 是物理上做不到 |
| 6 | 保留 C 端「支出不标红」的约定 | 这是 C 端 PRD 4.4.4 的产品硬约束，后台看流水时同样不应把支出染红 —— 保持口径一致 |
| 7 | 可看明细流水，但配套脱敏 + 留痕 | 客服排查「账对不上」必须看明细，这是被接受的隐私代价，用留痕来对冲 |
| 8 | 不做批量处置 | 误操作不可逆，逐个操作的摩擦在这里是特性不是缺陷 |
| 9 | 后台展示金额不重算口径 | C 端 6 个视图已定义口径（如转账不计入收支），后台重算必然产生分歧 |
| 10 | **现有 12 表 / 6 视图 / 8 约束一个字不改**，后台只 `CREATE TABLE` 建自己的新表 | C 端结构是已用 `_verify.sh` 全绿验证过的资产，后台迭代的收益远小于改坏主库的风险。代价是后台拿不到「用户表上加一列」这种便利，只能用独立新表 + 逻辑关联来换（见文首硬约束 R1–R3） |

## 8. 里程碑建议

按依赖关系排序，每一步都有可验证的产出。

| 阶段 | 内容 | 产出验证 |
| --- | --- | --- |
| **M1 地基** | `admin_user` + `admin_audit_log` 建表、独立鉴权、登录页 | 后台能登录；C 端 token 调后台接口被拒（反向也测）；每条写操作有审计行 |
| **M2 用户管理 + 处置** | 用户列表 / 搜索 / 详情、六项处置动作、审计接入 | 停用一个测试账号 → 该账号已登录的会话下一次请求即被拒；解锁后能立刻登录 |
| **M3 用户数据只读** | 五个 Tab、数据导出、查看留痕 | 后台展示的金额与 C 端页面对同一账本完全一致 |
| **M4 运营配置** | 关键词规则管理（先）；分类模板落表（后） | 新增一条规则后，在 C 端记账面板输入对应商户名能命中该分类 |
| **M5 数据看板** | 埋点落地 + 看板 | 能算出 DAU 与留存；指标口径与 PRD 9.3 一致 |

> M4 的关键词规则部分**不依赖任何前置**，如果排期紧张可以提前与 M2 并行。

> **建表脚本放在新文件里，不要动 `01_schema.sql`。** 后台的新表 DDL 应单独放（例如 `数据库脚本/99_admin_schema.sql`），与 C 端脚本物理分开 —— 这样既让「结构冻结」这件事在文件层面可见，也避免了重跑 C 端脚本时误伤后台表。

## 1. 产品概述

### 1.1 一句话定位

**一个把预算穿透到每一笔记录里的记账工具——记的时候就知道还剩多少。**

产品从**个人记账**起步，逐步覆盖**情侣**与**家庭**共同记账场景。这三类群体共享同一套底座（记录 + 预算管控），差异只在于"账本是私有的还是共享的"，因此可以在同一产品内平滑演进。

> **关于小微企业：** 小微企业的记账需求（经营流水、应收应付、发票管理、员工报销、税务申报）与个人消费记账重叠度极低，本质上是另一个产品。本产品**不覆盖**该场景，相关规划见 [10.2 后续版本与群体演进](#102-后续版本与群体演进) 的独立产品线说明。

### 1.2 背景与问题

记账类产品是一个高度拥挤的赛道，但用户的真实痛点从未被真正解决。我们在需求调研中发现三个反复出现的问题：

**问题一：记账坚持不下来。**
绝大多数记账 App 的用户，在下载后的第 3~7 天就停止记录。原因不是"没时间"，而是**记账本身没有即时回报**。用户花了 5 秒记一笔，得到的只是一条躺在列表里的流水，看不到这件事带来了什么价值。

**问题二：冷启动没有数据，看不到意义。**
新用户打开 App，所有图表都是空的。"你本月支出 ¥0"对一个刚下载的用户毫无意义。他必须连续记 30 天，才能看到第一张有价值的月度报告——而这 30 天里他没有任何正反馈。

**问题三：预算和记账是割裂的两个功能。**
用户设了月度预算，但这个预算只存在于"预算"页面。记账时不会提示，超支时不会预警，等到月底打开一看——"哦，超了 800"。**预算是事后审计，不是事前管控。**

### 1.3 产品策略

针对上述三个问题，V1.0 的核心策略是：**先看见，再管住。**

| 问题 | 策略 | 对应功能 |
| --- | --- | --- |
| 冷启动无数据 | 引导导入历史账单，注册当天就能看到上月消费画像 | 账单导入 |
| 记账无即时回报 | 每保存一笔，立即反馈"本月 XX 分类还剩 ¥N" | 预算穿透 |
| 预算管控失效 | 把剩余预算摊到剩余天数，给出"今日可花"额度 | 今日可花 |
| 记账坚持不下来 | 记账全流程压到 3 秒内，键盘优先、连续记账 | 极速记账 |

### 1.4 差异化价值主张

> 其他工具告诉你"你花了多少"，明账告诉你"你还能花多少"。

### 1.5 产品目标（V1.0）

**北极星指标：周活跃记账天数**
衡量的是用户是否真正养成了习惯，而非仅仅注册了账号。

| 层级 | 指标 | 目标值 |
| --- | --- | --- |
| 北极星 | 活跃用户周均记账天数 | ≥ 4 天 |
| 留存 | 次日留存 / 7 日留存 / 30 日留存 | 55% / 35% / 20% |
| 核心行为 | 注册用户中完成首笔记账的比例 | ≥ 80% |
| 核心行为 | 单笔记账耗时（中位数） | ≤ 8 秒 |
| 功能渗透 | 完成账单导入的用户占比 | ≥ 40% |
| 功能渗透 | 设置预算的用户占比 | ≥ 50% |

> 以上指标均针对 V1.0 的核心用户（个人）。扩展群体（情侣 / 家庭）的指标在 V1.4 启动时另行制定，不纳入 V1.0 的考核范围。

## 2. 目标用户与使用场景

### 2.1 用户画像

产品服务三类记账主体，按"何时服务"分层。**V1.0 只交付核心用户（个人）的完整体验**，扩展用户的需求在路线图中逐步落地。

```
┌─────────────────────────────────────────────────────┐
│  第三层：小微企业 / 个体经营                          │
│  独立产品线，不在本产品范围内（见 10.2）              │
├─────────────────────────────────────────────────────┤
│  第二层：情侣 / 家庭          ← V1.2 - V2.0 落地     │
│  共享账本 + 分摊 + 共同预算                          │
├─────────────────────────────────────────────────────┤
│  第一层：个人                 ← V1.0 核心交付        │
│  私有账本 + 预算管控 + 消费洞察                       │
└─────────────────────────────────────────────────────┘
```

#### 2.1.1 核心用户：个人（V1.0 服务对象）

**22-35 岁的城市上班族**

- 有稳定收入，月薪 ¥6,000 ~ ¥25,000
- 有"钱不知道花哪了"的焦虑，但从未成功坚持记账超过一个月
- 手机支付为主（微信/支付宝占比 > 90%），现金几乎不用
- 主要设备是手机，但办公时间在电脑前

**用户特征对产品设计的影响：**

| 特征 | 设计含义 |
| --- | --- |
| 主要用手机，但办公在电脑 | V1.0 做响应式 Web，手机浏览器体验优先，桌面端顺手可用 |
| 支付以微信/支付宝为主 | 账单导入优先适配这两个渠道 |
| 有过记账失败经历 | 冷启动破冰是第一优先级，不能让他再经历"空白图表" |
| 时间碎片化 | 记账必须能在等电梯的 10 秒内完成 |

#### 2.1.2 扩展用户：情侣（V1.2 - V2.0）

**24-35 岁、处于恋爱或同居关系的双方**

| 维度 | 说明 |
| --- | --- |
| 核心诉求 | "我们花了多少" + "这次该谁付" |
| 与个人记账的差异 | 需要**共享账本**、**分摊规则**（AA / 按比例）、**结算记录**（谁欠谁多少） |
| 典型痛点 | 用 Excel 或微信群记账，月底对不上账；一方记账另一方看不到 |
| 关键功能 | 双人共享账本、AA 分摊、共同预算、结算提醒 |
| 数据敏感度 | 极高——需要**共享账本 + 私有账本并存**，允许部分消费不共享 |

> **设计要点：** 情侣场景下"隐私"是比"便利"更强的诉求。必须支持"这一笔仅自己可见"，否则用户会为了避免被看见而改用其他工具。

#### 2.1.3 扩展用户：家庭（V2.0+）

**已婚 / 有子女的 28-45 岁家庭**

| 维度 | 说明 |
| --- | --- |
| 核心诉求 | 家庭整体开销的掌控 + 中长期目标储备 |
| 与个人记账的差异 | **多成员账本**（2 人以上）、**角色权限**（管理员/成员）、**家庭预算**、**长期目标**（买房、教育金、旅行） |
| 典型痛点 | 房贷、教育、日常开销混在一起看不清；夫妻双方各记各的，家庭总账无人掌握 |
| 关键功能 | 家庭账本、成员贡献统计、固定支出管理（房贷/物业/学费）、家庭预算、目标储蓄 |
| 与情侣场景的关系 | 家庭是情侣场景的**超集**：成员数更多、无需结算（钱是共同的）、增加长期目标 |

> **设计要点：** 家庭场景不需要"谁欠谁"的结算逻辑，但需要"**固定支出**"这个关键概念——房贷、车贷、物业费、子女学费每月必然发生。这也是 [待定问题 #5](#12-待定问题open-questions) 中"今日可花是否扣除固定支出"的最终答案所在。

#### 2.1.4 三类群体的需求对照

| 维度 | 个人 | 情侣 | 家庭 |
| --- | --- | --- | --- |
| 账本结构 | 单账本 | 共享 + 私有双账本 | 共享家庭账本 |
| 成员数 | 1 | 2 | 2 - 6 |
| 分摊结算 | 无 | **AA / 按比例，需结算** | 无需结算（共同财产） |
| 预算模型 | 个人预算 | 共同预算 + 个人预算 | 家庭预算 + 成员零花钱 |
| 固定支出 | 可选 | 可选 | **核心需求**（房贷/学费） |
| 长期目标 | 无 | 可选 | **核心需求**（教育金/购房） |
| 权限模型 | 无 | 对等 | 管理员 / 成员 |
| 隐私诉求 | 无 | **极高** | 中 |

**结论：三类群体共享"记录 + 预算"底座，差异集中在共享层。** 因此 V1.0 只要把个人场景的底座做扎实，扩展群体的边际成本是可控的。

### 2.2 核心场景

**场景 A：日常即时记账（高频，占比 ~70%）**
> 中午 12:30，小李在公司楼下买了碗牛肉面，扫码付款 28 元。走出店门等电梯的间隙，他打开明账，点 "+"，输入 28，点"餐饮"，保存。屏幕上方提示"本月餐饮还剩 ¥342"。整个过程 6 秒。

**场景 B：睡前补记（中频，占比 ~20%）**
> 晚上 11 点，小李某天忘了记三笔。他打开流水页，按今天的日期逐条补记，或者直接看微信账单把当天几笔一次性记完。

**场景 C：月度复盘与账单导入（低频，每月 1-2 次，占比 ~10%）**
> 月初，小李收到信用卡账单，打开明账的导入功能，粘贴支付宝月度账单，系统自动解析出 40 多笔交易，去重后新增 12 笔，他扫一眼确认，点击导入。

**场景 D：预算告急（触发式）**
> 月中，小李打开首页，看到"今日可花 ¥86"，而他想买一双 ¥699 的鞋。他意识到这个月餐饮超支了，决定缓一缓。

### 2.3 用户旅程与关键节点

```
认知 → 注册 → 【冷启动破冰】→ 首次记账 → 日常记账循环 → 预算设置 → 月度复盘
                    ↑                              ↓
              ★ 最大流失点                    ★ 习惯养成关键期（前 7 天）
```

**关键流失点分析：**

| 节点 | 流失原因 | 应对设计 |
| --- | --- | --- |
| 注册后无数据 | 图表全空，看不到价值 | 引导导入历史账单，立刻生成消费画像 |
| 第 1-3 天 | 重复劳动，无反馈 | 极速记账 + 每笔预算反馈 |
| 第 4-7 天 | 新鲜感消退 | 消费日历打卡视觉成就、周报推送 |
| 月中 | 预算超支后破罐破摔 | 超支柔性提示 + 下半月补救建议 |

## 4. 功能详细规格

### 4.1 账号体系

#### 4.1.1 免登录试用（P0）

**设计理由：** 记账类产品的注册转化漏斗中，每增加一步注册流程，转化率下降约 20%。因此首屏不强制登录。

**流程：**
1. 用户首次访问 → 直接进入首页（本地存储，IndexedDB）
2. 首页顶部展示轻提示条：「数据保存在本机，登录后可多设备同步 →」
3. 用户完成第 1 笔记账后，或访问超出 3 个页面后，弹出一次注册引导（可关闭，7 天内不再打扰）
4. 用户注册时，将本地数据全量迁移至云端账号

**边界情况：**
- 本地已存在数据时，注册后需提供「合并到当前账号」/「绑定到新账号」的选择
- 本地数据迁移失败时，保留本地数据并在设置页提供「重试迁移」入口

#### 4.1.2 注册与登录（P0）

| 项 | 规格 |
| --- | --- |
| 方式 | 手机号+验证码、邮箱+密码、微信授权、Apple 登录 |
| 密码规则 | 8-32 位，需含字母+数字 |
| 找回密码 | 邮箱重置链接 / 手机验证码 |
| 会话保持 | Token 有效期 30 天，支持自动续期 |
| 安全 | 密码 bcrypt 加密存储；登录失败 5 次锁定 15 分钟 |

### 4.2 极速记账（核心模块）

**这是整个产品的生命线。目标是单笔记账 ≤ 8 秒（中位数），理想状态 3-5 秒。**

#### 4.2.1 记账面板

**交互形态：** 底部抽屉式面板（Bottom Sheet），**不跳转整页**。原因是整页跳转会产生"进入-填写-返回"的心理负担，抽屉面板让用户感觉随时可以退出，降低启动门槛。

```
┌─────────────────────────────────┐
│  支出  │  收入  │  转账          │ ← Tab 切换
├─────────────────────────────────┤
│                        ¥ 28.00  │ ← 金额显示区（大字号）
├─────────────────────────────────┤
│  [餐饮] [交通] [购物] [居家]     │   ← 分类九宫格
│  [娱乐] [医疗] [学习] [其他]     │      常用分类自动前置
│  [更多...]                      │
├─────────────────────────────────┤
│  账户: 微信钱包 ▾  时间: 今天 12:30 ▾ │
│  备注: 牛肉面                    │
├─────────────────────────────────┤
│  1   2   3   保存               │ ← 数字键盘常驻
│  4   5   6                      │
│  7   8   9   [ + - × ÷ ]        │
│  .   0   ⌫                      │
└─────────────────────────────────┘
```

**关键设计点：**

1. **键盘常驻。** 面板打开即展开数字键盘，不需要用户额外点击金额输入框。省掉一次点击 = 省掉 ~1.5 秒。

2. **金额四则运算。** 输入框支持 `12+35-8` 这样的表达式，实时显示计算结果。这是记账高频需求（凑单、AA、拆分），在键盘上提供 `+ - × ÷` 快捷键。

3. **分类九宫格 + 常用前置。** 按用户历史使用频次排序，最近 7 天用过的分类自动排到前面。默认高亮"上次使用"的分类，用户直接点保存即可完成一笔。

4. **账户与时间可折叠。** 默认使用"上次账户"和"当前时间"，这两项藏在折叠区，不占用视觉焦点。90% 的场景不需要展开。

5. **备注栏智能联想。** 输入时联想历史备注（如输入"牛"联想出"牛肉面"），选中后自动关联历史分类。

#### 4.2.2 保存后的即时反馈（预算穿透，核心差异化）

**这笔保存后，页面不跳转，面板收起，同时在首页顶部显示一条 2 秒的反馈条：**

```
✓ 已记录 ¥28.00 · 本月餐饮还剩 ¥342
```

**设计理由：** 这是把"预算"从独立页面拉进记账动作的关键。用户在记账的瞬间就获得预算信息，形成"记账 = 知道还剩多少"的认知关联。这条反馈是整个产品最核心的体验差异点。

**反馈内容规则：**

| 情况 | 反馈文案 |
| --- | --- |
| 无该分类预算 | `✓ 已记录 ¥28.00 · 本月餐饮已花 ¥658` |
| 有分类预算，未超支 | `✓ 已记录 ¥28.00 · 本月餐饮还剩 ¥342` |
| 有分类预算，剩余 < 20% | `⚠️ 已记录 ¥28.00 · 本月餐饮仅剩 ¥42` |
| 已超支 | `⚠️ 已记录 ¥28.00 · 本月餐饮已超支 ¥158` |
| 本月总预算剩余 < 20% | 在分类反馈后追加 `· 本月总额度剩余不足 20%` |

#### 4.2.3 连续记账（P1）

**场景：** 补记多笔消费时，反复打开面板很烦。

**设计：** 记账面板右上角提供「连续记账」开关。开启后，保存一笔时面板不关闭，仅清空金额与备注，保留分类和账户上下文，并显示已记录条数（如"已连续记录 3 笔"）。用户点击面板外区域退出。

#### 4.2.4 智能分类推荐（P2，V1.0 部分实现）

**V1.0 实现范围：** 基于备注关键词的规则匹配。

**规则示例：**

| 命中关键词 | 推荐分类 |
| --- | --- |
| 美团、饿了么、肯德基、麦当劳、星巴克 | 餐饮 |
| 滴滴、地铁、公交、加油、停车 | 交通 |
| 淘宝、京东、拼多多、天猫 | 购物 |
| 房租、物业、水电 | 居住 |
| 电影、KTV、游戏 | 娱乐 |

**V1.1 规划：** 基于用户历史记录建立个性化映射（同一商户/备注优先匹配用户曾选过的分类）。

#### 4.2.5 记账字段定义

| 字段 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- |
| 类型 | 是 | 支出 | 支出 / 收入 / 转账 |
| 金额 | 是 | 空 | 正数，最多 2 位小数，上限 9,999,999.99 |
| 分类 | 是 | 上次使用 / 餐饮 | 支出分类、收入分类分两套 |
| 账户 | 是 | 上次使用 | 转账时需选择转出/转入两个账户 |
| 时间 | 是 | 当前时间 | 可精确到分钟，支持跨天补记 |
| 备注 | 否 | 空 | 最长 100 字符 |
| 商户 | 否 | 空 | 由账单导入时填充，手动记账隐藏（并入备注） |

### 4.3 账单导入

**设计理由：** 解决冷启动问题。让用户注册当天就能看到有价值的历史数据。

#### 4.3.1 导入入口

设置页 → 账单导入，同时在新用户引导流程中作为第二步强引导。

#### 4.3.2 导入方式

**方式一：粘贴文本（P0）**

用户从支付宝/微信账单详情页复制交易记录文本，粘贴到输入框。

```
支付宝账单文本格式示例：

09-15 12:30  麦当劳(国贸店)        -28.00
09-15 08:15  滴滴出行              -23.50
09-14 19:45  美团外卖              -45.80
09-14 10:00  余额宝-转入           +1000.00
```

解析规则：
- 正则提取：`日期` + `时间` + `商户/描述` + `金额` + `收支方向`
- 日期补全年份（若解析出的日期晚于当前日期，则归为上一年）
- 金额符号：`-` 为支出，`+` 为收入

**方式二：CSV 文件上传（P0）**

支持支付宝网页版导出的 CSV 账单文件。

| 渠道 | 文件格式 | 编码 | 处理要点 |
| --- | --- | --- | --- |
| 支付宝 | CSV | GBK / UTF-8 | 需做编码嗅探；文件头有 4 行说明，需跳过 |
| 微信 | 加密 CSV 压缩包 | UTF-8 | 需用户输入解压密码（6 位），浏览器端解压 |

**技术说明：** 文件在**浏览器端解析**，不经过服务端，降低隐私顾虑与服务器压力。仅解析后的结构化结果上传。

#### 4.3.3 解析结果预览与确认

```
┌─────────────────────────────────────────┐
│  解析完成：共 47 笔                       │
├─────────────────────────────────────────┤
│  ⚠️ 检测到 12 笔疑似重复，已自动排除       │
│     [查看重复项]                          │
├─────────────────────────────────────────┤
│  ☑ 09-15 麦当劳          ¥28.00   餐饮 ▾ │
│  ☑ 09-15 滴滴出行        ¥23.50   交通 ▾ │
│  ☐ 09-14 余额宝转入    +¥1000.00  转账 ▾ │
│  ...                                     │
├─────────────────────────────────────────┤
│  已选 35 笔 · 合计支出 ¥1,284.50          │
│              [ 取消 ]  [ 确认导入 ]       │
└─────────────────────────────────────────┘
```

**关键设计点：**

1. **去重必须准确。** 去重规则：`金额相同` AND `日期相同` AND `商户名称相似度 > 80%`。去重是导入功能最容易被用户诟病的地方，宁可轻微漏判也不可误判。

2. **默认智能勾选。** 支出默认勾选，收入默认勾选，转账类默认不勾选（因为转账不是消费）。

3. **分类可逐个修正。** 每行右侧的分类下拉可修改，修改后同类商户自动同步（如把"麦当劳"改成"餐饮"，后续同类自动应用）。

4. **导入后可撤销。** 导入完成后提供「撤销本次导入」按钮，有效期 10 分钟。

#### 4.3.4 导入历史

记录每次导入的批次（时间、来源、笔数、状态），支持查看和整批撤销。

### 4.4 预算管控（核心模块）

#### 4.4.1 预算类型

| 类型 | 说明 | 优先级 |
| --- | --- | --- |
| 总预算 | 每月总支出上限 | P0 |
| 分类预算 | 特定分类的月度上限（如餐饮 ¥1500） | P0 |
| 周期 | V1.0 固定为自然月（1 日 - 月末） | P0 |

#### 4.4.2 今日可花（核心差异化功能）

**定义：**

```
今日可花 = (本月剩余预算 - 本月剩余固定支出预估) / 本月剩余天数
```

V1.0 简化实现：

```
今日可花 = 本月剩余预算 / 本月剩余天数
```

**展示位置：** 首页最显眼的大卡片，字号最大。

```
┌───────────────────────────────────┐
│  今日可花                          │
│  ¥ 86                             │  ← 超大字号
│  本月剩余 ¥1,720 · 剩余 20 天       │
│  ▓▓▓▓▓▓░░░░░░░░  已用 42%          │
└───────────────────────────────────┘
```

**设计理由：** 月度预算对用户来说是抽象数字。"还剩 ¥1720" 无法指导今天的决策；"今天能花 ¥86" 可以。这个功能把预算从"月度审计"变成"每日指导"。

**边界规则：**

| 情况 | 展示 |
| --- | --- |
| 未设置预算 | 显示"设置预算，知道今天能花多少 →"，引导设置 |
| 剩余预算 > 0，剩余天数 > 0 | 正常显示今日可花额度 |
| 剩余预算 ≤ 0 | 显示 `¥0`，文案改为"本月预算已用完"，标红 |
| 月末最后一天 | 今日可花 = 全部剩余预算 |

#### 4.4.3 预算设置页

```
┌─────────────────────────────────────┐
│  月度总预算                          │
│  ¥ 3,000              [ 修改 ]       │
│  ▓▓▓▓▓▓▓░░░░░  已用 ¥1,280 (42.7%)  │
├─────────────────────────────────────┤
│  分类预算                            │
│  餐饮    ¥1,500  已用 ¥1,158  77% ▓▓▓│
│  交通    ¥400    已用 ¥128    32% ▓░ │
│  购物    ¥600    已用 ¥0      0%  ░░ │
│  娱乐    ¥300    已用 ¥286    95% ▓▓▓│ ⚠️
│                    [ + 添加分类预算 ] │
├─────────────────────────────────────┤
│  ℹ️ 分类预算合计 ¥2,800，未超出总预算 │
└─────────────────────────────────────┘
```

**校验规则：**
- 分类预算合计 > 总预算时，给出提示但不阻断（允许用户如此设置，因为分类预算只是重点管控项，并非全部支出）
- 分类预算为空时，该分类从"今日可花"计算中排除

#### 4.4.4 超支预警（P1）

**触发时机：**

| 触发条件 | 提示方式 |
| --- | --- |
| 单笔记账后，某分类剩余 < 20% | 记账反馈条中标注 ⚠️ |
| 某分类超支 | 记账反馈条标红 + 首页预算卡片高亮 |
| 本月总预算剩余 < 20% | 首页顶部黄色提示条 |
| 本月总预算超支 | 首页预算卡片转为红色，文案提供"调整预算"入口 |

**设计原则：** 预警要**柔性**。绝不用弹窗打断用户记账——那会让用户为了避免看到提示而放弃记账。所有预警都以内联提示的形式出现。

## 6. 数据模型

### 6.1 核心实体

```
User（用户）
├── id, phone, email, password_hash, created_at
└── 1:N → Account, Category, Transaction, Budget

Account（账户）
├── id, user_id, name, type, icon, initial_balance, sort_order, is_archived
└── type: cash | wechat | alipay | bank | credit

Category（分类）
├── id, user_id, name, type, icon, color, parent_id, sort_order, is_system
└── type: expense | income

Transaction（交易）
├── id, user_id, type, amount, category_id, account_id, to_account_id,
│   happened_at, note, merchant, source, import_batch_id, created_at, updated_at
├── type: expense | income | transfer
└── source: manual | import_text | import_csv

Budget（预算）
├── id, user_id, period_type, period_value, total_amount, created_at
└── period_type: monthly

BudgetCategory（分类预算）
├── id, budget_id, category_id, amount

ImportBatch（导入批次）
├── id, user_id, source, file_name, total_count, imported_count,
│   skipped_count, status, created_at
└── status: pending | completed | reverted
```

### 6.2 关键索引

| 表 | 索引 | 用途 |
| --- | --- | --- |
| Transaction | `(user_id, happened_at DESC)` | 流水列表、统计聚合 |
| Transaction | `(user_id, category_id, happened_at)` | 分类统计、预算计算 |
| Transaction | `(user_id, amount, happened_at)` | 导入去重 |

### 6.3 数据一致性要求

- 转账操作需原子性写入（转出、转入两条记录，或单条记录带双账户）
- **建议采用单条记录 + `to_account_id` 的设计**，避免两条记录不同步的问题
- 账户余额为**计算值**，不存储，由流水实时聚合得出

### 6.4 为共享账本预留的设计（V1.0 必须做对的一件事）

V1.0 不做共享账本，但**数据模型必须现在就为它留好位置**。原因：把 `Transaction` 直接挂在 `User` 下，将来引入共享账本时需要做数据迁移和全量改造；而**现在多加一层 `Ledger` 的成本几乎为零**。

**V1.0 采用的结构（单用户也走账本层）：**

```
User
└── 1:N → Ledger（账本）
          ├── type: personal | couple | family
          ├── owner_id
          └── 1:N → Account, Category, Transaction, Budget
```

**V1.0 的行为约定：**

- 每个新用户注册时，自动创建一个 `type = personal` 的默认账本
- 所有查询与写入都带 `ledger_id`，但 UI 不暴露"账本"概念——用户感知不到这一层
- `Transaction` / `Budget` / `Account` / `Category` 表均增加 `ledger_id` 字段与索引

**为未来预留的扩展点（V1.0 不实现，仅预留字段与结构）：**

| 预留项 | 说明 |
| --- | --- |
| `LedgerMember` 表 | 账本成员及角色（V1.2 引入） |
| `Transaction.visibility` | `shared` / `private`，支撑"这一笔仅自己可见"（V1.2） |
| `Transaction.split` | 分摊规则与分摊明细（V1.2） |
| `Ledger.settlement` | 情侣场景的结算记录（V1.2） |

> **这是本项目中唯一一处"为未来设计"的地方。** 理由是：账本层的迁移成本极高且会阻塞 V1.2 的整个排期，而 V1.0 引入它的成本可以忽略。其余所有功能一律不为未来做额外设计。

## 7. 交互设计要点

### 7.1 核心原则

| 原则 | 说明 |
| --- | --- |
| **3 秒原则** | 任何高频操作（记账、查看今日可花）必须在 3 秒内完成 |
| **零跳转** | 记账、编辑等核心操作使用浮层，不跳转整页 |
| **不打断** | 所有提示（预警、引导、错误）均为内联或 Toast，禁止 modal 弹窗打断记账流 |
| **容错优先** | 删除可撤销、导入可回滚、编辑可取消 |
| **离线可用** | 核心记账功能在断网时可用，联网后自动同步 |

### 7.2 关键微交互

| 场景 | 反馈 |
| --- | --- |
| 保存成功 | Toast："✓ 已记录 ¥28 · 本月餐饮还剩 ¥342"（2s） |
| 记账面板打开 | 从底部滑出，200ms，缓动 ease-out |
| 金额输入 | 每次按键有轻微震动反馈（移动端） |
| 分类选中 | 图标放大 1.1x + 背景色填充，150ms |
| 预算超支 | 进度条变红 + 轻微抖动动画（1 次，不循环） |
| 删除流水 | 条目左滑淡出，底部出现撤销条（5s） |

### 7.3 空状态设计

| 页面 | 空状态 |
| --- | --- |
| 首页（无数据） | "还没有记录。导入账单快速开始，或直接记一笔" + 两个按钮 |
| 流水（无数据） | "这里会显示你的每一笔记录" + 记账按钮 |
| 统计（无数据） | "记录满 3 天后，这里会出现你的消费洞察"（给出明确的预期） |
| 预算（未设置） | "设置预算，知道今天能花多少" + 智能推荐额度的按钮 |

**空状态是冷启动的关键。** 每一个空状态都必须提供明确的下一步动作，绝不出现"暂无数据"这类无信息的占位。

| 风险 | 影响 | 概率 | 对策 |
| --- | --- | --- | --- |

| **数据安全与隐私顾虑** | 高 | 低 | 账单文件浏览器端解析；提供数据导出和彻底删除；隐私政策清晰透明 |
| **分类体系过于复杂导致记账变慢** | 中 | 中 | 默认分类精简为 10 个；常用分类动态前置；不强制选二级分类 |

## 13. 视觉设计规范（配色系统）

### 13.1 配色理念

**品牌色定为「青（Teal）+ 青蓝（Cyan）」双色主调。**

选择这个色系的依据有三层：

**依据一：行业验证。** 一项针对 42 款移动金融 App 配色聚类的研究显示，**冷色调主导的配色占比 40.5%**，是最主流的模式；研究将其归因于色彩情境理论——冷色传递信任、可靠、专业与稳定。

**依据二：与产品定位契合。** 我们的产品核心是**预算管控**，这要求界面传递"冷静、理性、克制"的情绪，而不是"消费、刺激、冲动"。青色位于蓝绿之间，既有蓝色的冷静可信，又比蓝色多一分活力，**不会像红色/橙色那样诱发消费冲动**。

**依据三：青色系天然适配金融数据的可视化。** 青色到青蓝的色相跨度，恰好可以延展出一套从青绿到靛蓝的和谐图表色板（见 13.6），比单一蓝色更容易区分多个分类。

参考案例：

| 产品 | 配色 | 借鉴点 |
| --- | --- | --- |
| Kernel Wealth（NZ fintech） | 自然青绿 `#227b71` + 浅青 `#7dd4c8` + 暖奶油中性色 `#f9f7f4` | 青色作为主色的完整层级设计 |
| Plaid（open finance） | 蓝 `#0A85FF` + 青 `#37D7FF` + 深墨底 `#0B1020` | 青蓝双色搭配 + 深色模式底色 |
| Cashly（个人理财） | "calm blue and teal palette" | 明确的"冷静蓝青"定位，与本产品目标一致 |
| iColorPalette "Blue and Grey" | 青 `#17879B` + 青绿 `#16A085` | 青与青蓝的邻近搭配 |

> **重要原则（源自参考案例的共性）：** 青色系的最佳实践是**作为主调 + 强调色，配合中性色构建层次**，而不是让整个界面铺满青色。本规范中，中性色承担 70% 以上的界面面积，青色用于品牌识别、关键操作与数据表达。

> **注意：本产品不定义独立的"成功绿"。** 因为青色本身就是绿蓝之间的颜色，再引入一个绿色会在视觉上产生歧义。成功状态一律使用主色青。

#### 13.5.2 金额的色彩约定（关键设计决策）

| 语义 | 颜色 | 说明 |
| --- | --- | --- |
| **支出金额** | `#0F172A`（slate-900）**中性深色** | **绝不标红** |
| **收入金额** | `#0D9488`（teal-600） | 使用品牌色，正向强调 |
| **转账金额** | `#64748B`（slate-500） | 灰色弱化，因为转账不是真实消费 |
| **预算进度正常** | `#0D9488`（teal-600） | |
| **预算进度 > 80%** | `#F59E0B`（amber-500） | |
| **预算超支** | `#E11D48`（rose-600） | |

> **为什么支出不标红？**
>
> 这是本产品配色中最重要的一条约定。记账类产品让支出标红是常见做法，但我们的用户**每天要记 5 笔以上支出**——如果每一笔都是红色，整个流水列表会变成一片刺眼的红，界面持续传递"你在花钱、你在犯错"的焦虑信号。
>
> 这与产品的核心目标直接冲突：**我们要让用户坚持记账，而不是让记账变成一种负罪感的提醒。**
>
> 因此我们把**红色完全保留给真正的异常**（超支、错误、删除）。这样一来，红色在界面中极其罕见——它出现的那一刻，用户一定会注意到。**稀缺性本身就是最强的警示信号。**

### 13.7 品牌渐变

| 名称 | 定义 | 用途 |
| --- | --- | --- |
| 品牌主渐变 | `linear-gradient(135deg, #14B8A6 0%, #06B6D4 100%)` | **「今日可花」卡片**、首页头部、空状态插图 |
| 深色渐变 | `linear-gradient(135deg, #0D9488 0%, #0E7490 100%)` | 按钮按下态、深色模式卡片 |
| 浅色渐变 | `linear-gradient(135deg, #F0FDFA 0%, #ECFEFF 100%)` | 卡片背景、引导区背景 |

> 品牌主渐变是"青 → 青蓝"最直接的视觉表达，也是产品最具识别度的视觉资产。**建议将其集中使用在「今日可花」这一核心卡片上**，让品牌色与产品最核心的功能形成绑定记忆。

| `surface-alt` | `#F1F5F9` | `#1A2438` | — |
| `border` | `#E2E8F0` | `#24304A` | — |

### 13.9 对比度校验

**所有配色组合上线前必须通过 WCAG AA 校验。** 以下为关键组合的实测对比度：

| 前景 | 背景 | 对比度 | 结论 |
| --- | --- | --- | --- |
| `#0F172A` 正文 | `#FFFFFF` | 17.85:1 | ✅ AAA |
| `#0F766E` 文字/按钮底 | `#FFFFFF` | 5.47:1 | ✅ AA（正文可用） |
| `#0F766E` 底的白色文字 | — | 5.47:1 | ✅ AA（正文可用） |
| `#64748B` 次要文字 | `#FFFFFF` | 4.76:1 | ✅ AA（正文可用） |
| `#E11D48` 错误文字 | `#FFFFFF` | 4.70:1 | ✅ AA（正文可用） |
| `#0D9488` 大字号数字 | `#FFFFFF` | 3.75:1 | ⚠️ 仅限大字号（≥ 18.66px Bold 或 ≥ 24px） |
| `#F59E0B` 预警文字 | `#FFFFFF` | 2.15:1 | ❌ **禁止用于文字**，仅可用于图标与背景 |
| `#14B8A6` 任何文字 | `#FFFFFF` | 2.49:1 | ❌ **禁止用于文字**，仅可用于图形 |

**由此推导出的硬性规则：**

| 场景 | 规范 |
| --- | --- |
| 主按钮 | 底色 `#0F766E`（teal-700）+ 白色文字 |
| 「今日可花」超大数字 | 颜色 `#0D9488`（teal-600），字号 ≥ 32px |
| 正文中的品牌色文字 | `#0F766E`（teal-700） |
| 预警文字 | 用 `#B45309`（amber-700）而非 `#F59E0B`，或改为图标 + 深色文字 |
| `#14B8A6` / `#F59E0B` | 只能作为**填充色、图标色、图表色**，永不作文字色 |

```
用户点击 "+"

首页数据实时更新
```

### A.2 账单导入流程

```
进入导入页
    ↓
选择方式：粘贴文本 / 上传 CSV
    ↓
浏览器端解析（不上传原始文件）
    ↓
提取：日期、时间、商户、金额、方向
    ↓
关键词自动分类
    ↓
去重检测（金额 + 日期 + 商户相似度）
    ↓
展示预览列表（重复项默认排除，可查看）
    ↓

    ↓

    ↓
```

### A.3 预算穿透流程

```
用户设置月度总预算与分类预算
    ↓
每次记账后触发预算重算
    ↓
计算：
  · 分类剩余 = 分类预算 - 本月该分类支出
  · 总剩余 = 总预算 - 本月总支出
  · 今日可花 = 总剩余 / 本月剩余天数
    ↓
判定状态：
  · 剩余 > 20%      → 正常展示
  · 剩余 0-20%      → 黄色预警 ⚠️
  · 剩余 < 0        → 红色告警，今日可花显示 ¥0
    ↓
反馈至：记账 Toast / 首页卡片 / 预算页进度条
```

## 附录 B：关键设计决策记录

| # | 决策 | 理由 | 备选方案 |
| --- | --- | --- | --- |
| 1 | 记账使用底部抽屉而非整页 | 降低启动心理成本，可随时退出 | 整页跳转（已否决：认知负担重） |
| 2 | 数字键盘常驻 | 省钱一次点击，约 1.5s | 点击金额框再展开（已否决） |
| 3 | 预算反馈放在记账 Toast 中 | 建立"记账=知道剩多少"的认知关联 | 仅在预算页展示（已否决：割裂） |
| 4 | 引入"今日可花" | 把抽象预算转为可指导当日决策的数字 | 仅显示月度剩余（已否决：不可执行） |
| 5 | 账单文件浏览器端解析 | 隐私顾虑低、服务器压力小 | 服务端解析（已否决） |
| 6 | 转账用单条记录 + 双账户字段 | 避免两条记录不同步的一致性风险 | 双记录（已否决） |
| 7 | 删除/导入均可撤销 | 记账数据是用户的敏感资产，误删代价高 | 二次确认弹窗（已保留，但增加撤销） |
| 8 | 所有预警用内联提示，禁用弹窗 | 弹窗会打断记账流，反而降低记账意愿 | Modal 弹窗（已否决） |
| 9 | V1.0 数据模型即引入 `Ledger` 层 | 账本层的迁移成本极高且会阻塞 V1.2 排期，而现在引入成本可忽略 | 直接挂 `User` 下（已否决：将来需结构性迁移） |
| 10 | V1.0 不服务情侣 / 家庭 | 个人场景尚未验证就做共享账本，会两头不到岸 | V1.0 直接做共享账本（已否决：工期翻倍且核心假设未验证） |
| 11 | 小微企业记账不纳入本产品 | 需求重叠度极低，强行合并会稀释产品定位 | 同产品内做"个人版/经营版"（已否决：两套数据模型与合规体系） |
| 12 | **支出金额不标红**，用中性深色 | 用户每天记 5+ 笔支出，全标红会让界面持续传递"你在犯错"的焦虑感，与"培养记账习惯"的目标直接冲突。红色只保留给超支等真正的异常，用稀缺性换取警示强度 | 支出标红（已否决：日常状态不应报警） |
| 13 | 配色直接采用 Tailwind 默认色板，不自定义色值 | 消除设计与开发之间的色值转换误差，可直接使用内置工具类；青色系是金融产品的行业主流选择，无需另造一套 | 自定义品牌色（已否决：收益低、易走样） |
